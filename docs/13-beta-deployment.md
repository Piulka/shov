# Первый сервер и Telegram-бета ШОВЬ

Статус: инструкция для версии 0.5.0. Основной сценарий по решению владельца: открытая бета, вход любому пользователю Telegram по ссылке. Список допуска остаётся дополнительным режимом. Готовая конфигурация предназначена для одного Linux VPS и одного процесса игры. Нагрузка, внешний HTTPS и реальные клиенты Telegram должны быть проверены на выбранном сервере до объявления ссылки игрокам.

## Что входит в поставку

- Node.js 24, собранный интерфейс и API в одном контейнере. Процесс приложения работает от UID/GID 1000; файловая система образа доступна только для чтения.
- Caddy автоматически выпускает и продлевает HTTPS-сертификат, перенаправляет HTTP на HTTPS и передаёт запросы приложению.
- Наружу опубликованы только порты Caddy 80 и 443. API 3001 доступен внутри Docker-сети. Административный API Caddy доступен только на его loopback.
- Сервер доверяет заголовкам прокси только от фиксированного IP Caddy `172.29.43.2`. При смене подсети необходимо одновременно изменить IP Caddy, IP приложения и `TRUSTED_PROXY` в Compose.
- Игра, резервные копии и сертификаты хранятся в отдельных постоянных Docker volumes. Пересборка контейнера не удаляет сохранения.
- Есть проверки доступности процесса/БД, перезапуск завершившихся контейнеров, ограничение объёма контейнерных логов и команды согласованного копирования SQLite.

Статус `unhealthy` сам по себе не перезапускает контейнер: `restart: unless-stopped` работает при завершении процесса. Проверку доступности и уведомления об ошибках нужно подключить к внешнему мониторингу.

## Что потребуется от владельца

1. Linux VPS с Docker Engine и плагином Docker Compose v2. Для начальных испытаний разумная отправная точка: 2 vCPU, 2 ГБ RAM, SSD от 20 ГБ. Это не обещание числа одновременных игроков; размеры уточняются нагрузочным тестом.
2. Домен или поддомен, например `game.example.com`. DNS-запись A должна указывать на VPS. AAAA добавляется только при работающем IPv6 на этом же сервере.
3. Telegram-бот, созданный через официальный `@BotFather`, и его токен.
4. Почтовый адрес для контакта ACME и отдельное место хранения копий вне VPS.

Разрешить входящий TCP 80/443, UDP 443 при использовании HTTP/3, SSH только с нужных адресов. Учитывать, что опубликованные Docker-порты могут обходить некоторые правила UFW; использовать firewall хостера и корректные Docker-правила. Порт 3001 наружу не публиковать. Подсеть `172.29.43.0/24` не должна пересекаться с существующей VPN/Docker-сетью.

## Первый запуск

Следующие команды выполняются на Linux VPS. В каталоге `/opt/shov` должна находиться одна копия проекта; постоянное имя Compose-проекта `shov` сохраняет имена volumes при обновлениях. Пользователь с доступом к Docker фактически имеет административные права на сервере.

```bash
git clone https://github.com/Piulka/shov.git /opt/shov
cd /opt/shov
cp .env.example .env
chmod 600 .env
nano .env
```

Задать реальные значения в `.env`:

```dotenv
APP_MODE=telegram
APP_ORIGIN=https://game.example.com
BOT_TOKEN=replace-with-the-token-from-BotFather
DATABASE_PATH=/data/shov.sqlite
BETA_ACCESS=open
BETA_TELEGRAM_IDS=
BLOCKED_TELEGRAM_IDS=
LOG_LEVEL=info
ACME_EMAIL=operator@example.com
SHOV_IMAGE_TAG=beta
```

`APP_ORIGIN` содержит ровно HTTPS origin без пути, query, fragment или логина. Он используется и сервером, и Caddy, поэтому домен не нужно дублировать в другом файле. Для контейнера `DATABASE_PATH` должен быть абсолютным путём внутри `/data`; значение `data/shov.sqlite` из локальной среды использовать нельзя. Compose фиксирует `APP_MODE=telegram`, адрес прослушивания и доверенный IP прокси независимо от локальных настроек. Токен никогда не помещать в исходники, URL, GitHub issue или скриншот конфигурации.

Зафиксировать тег образа по текущему коммиту и проверить конфигурацию, не выводя секреты:

```bash
release="$(git rev-parse --short=12 HEAD)"
sed -i "s/^SHOV_IMAGE_TAG=.*/SHOV_IMAGE_TAG=$release/" .env
docker compose --env-file .env -f deploy/compose.yaml config --quiet
docker compose --env-file .env -f deploy/compose.yaml build --pull
docker compose --env-file .env -f deploy/compose.yaml up -d --wait
docker compose --env-file .env -f deploy/compose.yaml ps
```

Не публиковать вывод `docker compose config` без `--quiet`: он содержит подставленные секреты. На VPS не требуются отдельные Node.js/npm, сборка выполняется внутри Docker. При первом запуске приложение автоматически создаст таблицы SQLite. Не запускать несколько экземпляров API против одного файла и не размещать SQLite на сетевом файловом хранилище.

Проверить `/api/health`, `/api/ready` и главную страницу снаружи. Проверку можно выполнить с рабочего компьютера с Node.js 24:

```bash
node tools/check-deploy.mjs https://game.example.com
```

Скрипт проверяет TLS, Telegram-режим, чтение БД, выдачу собранного интерфейса и отказ анонимному запросу состояния. Он не проверяет подлинный вход Telegram, игровой баланс или способность выдержать массовый заход.

## Подключение Telegram

В официальном `@BotFather` выбрать созданного бота в `/mybots` и открыть настройки Mini App. Названия пунктов могут меняться в клиенте BotFather.

1. Включить Main Mini App и указать ровно URL `https://game.example.com/`.
2. Настроить кнопку меню через Bot Settings → Menu Button или команду `/setmenubutton`: название `Играть`, URL тот же.
3. Проверить запуск из профиля бота и из кнопки меню на реальном устройстве. Ссылку основного Mini App обычно распространяют в виде `https://t.me/<bot_username>?startapp`; проверить её с фактическим именем бота.
4. Заполнить имя, описание, изображение приложения и страницу поддержки. Игрок должен видеть статус беты до входа.

Текущему приложению не нужен Telegram webhook: авторизация происходит через подписанные Telegram `initData`, которые сервер сверяет с токеном бота. Обычное открытие HTTPS-адреса браузером без Telegram не создаёт игровой аккаунт. Локальное сохранение привязано к локальному аккаунту и автоматически не превращается в Telegram-аккаунт. Первому настоящему входу соответствует новое сохранение; перенос тестового героя требует отдельной явной операции.

Проверить минимум Telegram Android, iOS и Desktop: первый вход, повторное открытие, сворачивание, возвращение после офлайна, безопасные области экрана, карту, сборку, бой, клан и отсутствие потери состояния. Playwright/Chrome не заменяет эти проверки Telegram WebView.

## Доступ к бете и операторская блокировка

`BETA_ACCESS=open` разрешает вход любому пользователю с подлинной авторизацией Telegram. `BETA_ACCESS=allowlist` допускает только Telegram ID из `BETA_TELEGRAM_IDS`, например `123456789,987654321`. Это числовые ID, не никнеймы и не номера телефона. В режиме списка пустой список никого не пропускает. Сервер вне Compose по умолчанию использует этот закрытый режим, чтобы пропуск переменной не открыл тест случайно.

`BLOCKED_TELEGRAM_IDS` принимает такой же список ID и имеет приоритет над открытой бетой/списком допуска. Блокировка проверяется также для уже выданных сессий. После изменения `.env` пересоздать приложение:

```bash
docker compose --env-file .env -f deploy/compose.yaml up -d --wait --force-recreate app
```

В игре также есть жалобы на сообщения клана и операторский CLI. Он сохраняет копию обжалуемого сообщения, аккаунт автора, решение и причину действия. Просмотреть очередь:

```bash
docker compose --env-file .env -f deploy/compose.yaml exec -T app node --import tsx tools/moderate.ts reports
```

Затем использовать реальные `ACCOUNT_ID`/`REPORT_ID` из результата. Для блокировки передаётся внутренний ID аккаунта, например `telegram:123456789`, а не просто число из `.env`:

```bash
docker compose --env-file .env -f deploy/compose.yaml exec -T app node --import tsx tools/moderate.ts block ACCOUNT_ID "Причина блокировки"
docker compose --env-file .env -f deploy/compose.yaml exec -T app node --import tsx tools/moderate.ts delete-message REPORT_ID "Причина удаления"
docker compose --env-file .env -f deploy/compose.yaml exec -T app node --import tsx tools/moderate.ts resolve REPORT_ID "Результат рассмотрения"
docker compose --env-file .env -f deploy/compose.yaml exec -T app node --import tsx tools/moderate.ts unblock ACCOUNT_ID "Причина разблокировки"
```

Блокировка через CLI вступает в силу на последующих запросах без перезапуска. Это минимальный операторский инструмент, а не готовая административная панель. Для открытого теста нужен указанный владельцем канал поддержки; порядок обработки жалоб, злоупотреблений и удаления пользовательских данных ещё предстоит организовать. Полноценные сезоны, экономика после последних текущих регионов и массовая эксплуатация не считаются завершёнными.

## Резервные копии

Обычное копирование живого `.sqlite` без его WAL не гарантирует сохранность последних записей. Команда ниже использует SQLite Online Backup API, затем `PRAGMA integrity_check` и `foreign_key_check`, и публикует новый файл без перезаписи существующего. SQLite продолжает обслуживать приложение; при интенсивной записи копирование может выполняться дольше.

```bash
docker compose --env-file .env -f deploy/compose.yaml run --rm --no-deps backup
```

Команда возвращает JSON с абсолютным путём `/backups/shov-<timestamp>-<suffix>.sqlite`. Код выхода должен быть нулевым. Файл находится в volume `shov_game-backups`, а не внутри контейнера приложения. Копия создаётся с правами `0600`. Снимок включает аккаунты, кланы, сообщения и сессии, поэтому хранится как чувствительные данные.

Установить автоматический запуск раз в шесть часов после успешной ручной проверки:

```bash
sudo install -m 0644 deploy/shov-backup.service /etc/systemd/system/shov-backup.service
sudo install -m 0644 deploy/shov-backup.timer /etc/systemd/system/shov-backup.timer
sudo systemctl daemon-reload
sudo systemctl enable --now shov-backup.timer
sudo systemctl start shov-backup.service
sudo systemctl status shov-backup.service --no-pager
sudo systemctl list-timers shov-backup.timer --no-pager
```

В service задан `/opt/shov` и `/usr/bin/docker`; при иной установке изменить эти пути. Журнал задания: `journalctl -u shov-backup.service`. Ошибка копирования должна вызывать уведомление оператора через выбранный мониторинг.

Шестичасовой график означает возможную потерю до шести часов прогресса только при исправном задании и наличии доступной копии. Он не даёт гарантии RPO при сбоях диска или задания. Копии на том же VPS не защищают от потери сервера. Таймер не отправляет файлы в облако и не удаляет старые автоматически.

До широкого приглашения игроков настроить отдельную отправку volume с копиями на другой сервер или в объектное хранилище, например Restic с шифрованием. Проверить восстановление именно из этой внешней копии. Рекомендуемая начальная политика: локально семь дней шестичасовых снимков, вне VPS четырнадцать дневных и восемь недельных. Удаление старых снимков включается только после проверки внешнего хранения и восстановления; секреты/пароль шифрования хранятся отдельно от VPS. До настройки удаления необходимо следить за свободным диском: таймер будет накапливать файлы.

## Восстановление

Восстановление не заменяет живой файл. Оно создаёт новый файл, проверяет его и отказывает, если целевой путь либо его `-wal`, `-shm`, `-journal` уже существуют. Ни приложение, ни другие процессы не должны открывать новый путь до завершения восстановления.

Пример для уже существующего снимка, имя которого взято из успешного результата backup:

```bash
docker compose --env-file .env -f deploy/compose.yaml stop app
docker compose --env-file .env -f deploy/compose.yaml run --rm --no-deps backup node tools/restore.mjs /backups/shov-REAL-TIMESTAMP-SUFFIX.sqlite /data/restored-2026-09-09.sqlite
nano .env
```

В `.env` поменять `DATABASE_PATH=/data/restored-2026-09-09.sqlite`. Путь должен совпадать с успешным результатом restore и оставаться внутри `/data`.

```bash
docker compose --env-file .env -f deploy/compose.yaml up -d --wait app
```

Проверить доступность, подлинный Telegram-вход и выбранные сохранения. Старый файл оставлен для диагностики; не удалять его до окончания проверки. При восстановлении потерянного VPS сначала доставить внешнюю копию в `shov_game-backups` с правами для UID 1000 и выполнить тот же сценарий. Ранее действовавшие сессии и списки кланов будут соответствовать моменту снимка.

Для тренировки восстановления выбрать отдельное имя, например `/data/restore-drill-<date>.sqlite`, выполнить restore и не менять `DATABASE_PATH`. Проверка структуры не доказывает правильность игровой логики: восстановленную БД следует отдельно открыть совместимой версией приложения и проверить ожидаемые аккаунты. Не подключать экспериментальную копию к публичной игре.

## Обновление и откат

Перед обновлением записать текущий commit, значение `SHOV_IMAGE_TAG` из `.env` и имя снимка. Не выводить весь `.env` в общий журнал. Сохранить предыдущий Docker-образ до принятия новой версии.

```bash
cd /opt/shov
docker compose --env-file .env -f deploy/compose.yaml run --rm --no-deps backup
git status --short
git pull --ff-only
release="$(git rev-parse --short=12 HEAD)"
sed -i "s/^SHOV_IMAGE_TAG=.*/SHOV_IMAGE_TAG=$release/" .env
docker compose --env-file .env -f deploy/compose.yaml config --quiet
docker compose --env-file .env -f deploy/compose.yaml build --pull
docker compose --env-file .env -f deploy/compose.yaml up -d --wait
docker compose --env-file .env -f deploy/compose.yaml logs --tail=100 app caddy
```

`git pull --ff-only` остановится при конфликтующей истории; не сбрасывать локальные изменения автоматически. При ошибке сборки работающий контейнер остаётся на старом образе; вернуть старый `SHOV_IMAGE_TAG` в `.env`, чтобы задания backup ссылались на существующий образ. При ошибке обновления сохранить лог и проверить БД, не повторять миграции вслепую.

Если новая версия не меняла сохранения несовместимым образом, вернуть прежний `SHOV_IMAGE_TAG` в `.env` и выполнить `up -d --wait --no-build`. Caddyfile включён в образ прокси, поэтому откатывается вместе с его тегом; изменение Caddyfile требует пересборки образа. Если сам Compose изменился в новом релизе, сверить его с прежним коммитом перед откатом. При несовместимых миграциях нужен старый образ вместе с предшествующим снимком: остановить приложение, восстановить снимок в новый путь, установить старый тег и этот `DATABASE_PATH`, затем запустить и проверить. Прогресс после снимка в таком откате теряется. Универсальная обратимость любых будущих миграций не обещается.

Не применять `docker compose down --volumes`: это удаляет сохранения и сертификаты. Не удалять старые образы до проверки обновления и восстановления. Настоящий план релиза должен заранее устанавливать ожидаемое короткое окно недоступности: этот комплект не реализует обновление без простоя.

## Граница готовности

Локальные автоматические проверки подтверждают сценарии резервного копирования открытой SQLite/WAL, целостность, восстановление независимой копии, отказ при повреждении и запрет перезаписи. Они не заменяют проверку Docker на Linux, выпуск реального сертификата, восстановление внешней копии, нагрузочный тест и запуск в настоящем Telegram.

Для публичного объявления беты должны быть выполнены эти операционные проверки, указан контакт поддержки и подключены уведомления о недоступности, ошибках копирования и заполнении диска. Первая бета может использовать текущие временные визуальные ассеты; их производственное обновление описано отдельно в документации проекта.
